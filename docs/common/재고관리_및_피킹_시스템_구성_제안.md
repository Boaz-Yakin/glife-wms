# [제안 및 분석] 재고(Inventory) 관리와 피킹(Picking) 시스템 아키텍처 비교 및 구성 방안

## 1. 개요 및 핵심 결론

창고 및 풀필먼트 운영에서 **재고 관리(Inventory Management)**와 **피킹(Picking)**을 하나의 단일 앱으로 구성해야 하는지, 혹은 별도 앱으로 분리해야 하는지에 대한 기술 및 현장 운영 관점의 아키텍처 분석입니다.

### 핵심 권장 전략 (Hybrid Architecture)
> **"데이터 및 백엔드 엔진은 단일 소스(Single Source of Truth)로 완전히 통합하되, 현장 작업 클라이언트(UI/UX)는 작업 특성에 맞게 반드시 전용 모드로 분리한다."**

* **데이터 & 백엔드 레이어 (Backend & DB): 통합 필수**
  * 재고 가용성 계산(`가용재고 = 총재고 - 할당/피킹중 - 이동중`)과 실시간 재고 차감, 동시성 제어(Concurrency Control)가 필수적이므로 백엔드나 DB 레벨을 물리적으로 분리하면 심각한 데이터 불일치 및 결품(Shortage)이 발생합니다.
* **현장 단말기/클라이언트 레이어 (Frontend & UI): 역할별 분리 권장**
  * 피킹 작업자는 **"1초당 1동선, 극도의 단순성(No-Click), 대형 폰트, 오디오/햅틱 피드백"**이 생명입니다.
  * 재고 관리자는 **"품목 검색, Lot/유통기한 추적, 로케이션 이동, 실사(Cycle Counting), 사유 코드 입력"** 등 고밀도 입력 화면이 필요합니다.
  * 동일한 앱 화면에 두 기능을 섞어두면 피킹 작업자의 조작 실수, 화면 이탈, 속도 저하를 초래합니다.

## 2. 통합 vs 분리 심층 비교

| 비교 항목 | 옵션 A: 완전 통합 앱 (메뉴 통합) | 옵션 B: 물리적 완전 분리 (별도 시스템/DB) | 옵션 C: 하이브리드 구성 (권장) |
| :--- | :--- | :--- | :--- |
| **시스템 구조** | 단일 앱 내에 재고조회, 입고, 피킹 메뉴 공존 | 별도 재고 WMS + 별도 피킹 시스템 분리 | **단일 백엔드/DB + 역할별 전용 웹/PWA 클라이언트 분리** |
| **현장 작업성 (피킹)** | 복잡한 UI, 작업 중 실수로 메뉴 이탈 위험 | 피킹 화면만 노출되어 단순함 | **전용 모드(독립 PWA)로 불필요한 네비게이션 원천 차단** |
| **데이터 정합성** | 완벽 (실시간 동기화) | 시스템 간 인터페이스 지연으로 재고 불일치 위험 | **완벽 (동일 Prisma/Postgres 트랜잭션 공유)** |
| **오프라인 대응력** | 번들이 무거워 오프라인 캐싱 부담 증가 | 피킹 전용 경량 오프라인 캐시 용이 | **피킹 라우트만 초경량 PWA로 서비스 워커 캐싱 최적화** |
| **개발 및 유지보수** | 초기 구축은 빠르나 코드 결합도 증가 | 두 시스템을 각각 개발/운영해야 하므로 비용 2배 | **단일 코드베이스에서 모듈식 개발, 도메인 로직 재사용** |

## 3. 세부 영역별 시스템 구성 제안

### 3.1 피킹 전용 시스템 (Picking Runner System)
* **주요 사용자**: 창고 피킹 작업자 (Pickers)
* **장비 환경**: 손목형 PDA + 핑거 링 스캐너(Ring Scanner), 작업자 스마트폰 (PWA)
* **주요 기능 및 워크플로우**:
  1. **No-Click 인터페이스**: 화면 터치 조작 없이 오직 바코드 스캔(로케이션 → 상품)과 비프음/음성 안내로만 공정 진행.
  2. **최단 경로 가이드**: 2개 통로 3단 랙 환경에 맞춘 S-Shape 동선 자동 소팅.
  3. **Cold Chain 관리**: 상온 구역(Zone A) 피킹 100% 완료 시점에만 냉동 차량 구역(Zone F) 경로 개방.
  4. **명령 바코드(Command Barcode)**: 
     - `CMD-SKIP`: 재고 없음/패스 (즉시 다음 로케이션 안내 + 재고 시스템에 불일치 알림 전송)
     - `CMD-UNDO`: 직전 오스캔 취소 및 원복
     - `CMD-DONE`: 작업 강제 종료 및 전송

### 3.2 재고 관리 시스템 (Inventory Management System)
* **주요 사용자**: 창고 관리자, 입고 검수원, 지게차 작업자 (사무실 PC + 현장 태블릿)
* **장비 환경**: 데스크톱 웹 브라우저, 산업용 태블릿, 바코드 라벨 프린터
* **주요 기능 모듈**:
  1. **입고 및 적치 (Inbound / Put-away)**: 
     - 사전 입고 정보(ASN) 대조 검수
     - SKU별 보관 규칙(상온/냉동, 회전율)에 따른 비어있는 최적 랙 로케이션 추천
  2. **로케이션 이동 및 보충 (Bin Transfer & Replenishment)**:
     - 대량 보관 구역(Reserve)에서 전면 피킹 구역(Active Pick Face)으로의 재고 보충 지시
     - 파렛트/박스 단위 이동 기록
  3. **순환 재고 실사 (Cycle Counting)**:
     - 품목별 정기 실사 및 피킹 중 `CMD-SKIP` 발생 로케이션 대상 수시 실사 오더 발행
     - 전산 재고와 실물 재고 오차 조정 및 로깅
  4. **재고 마스터 및 이력 관리 (Master & Audit)**:
     - SKU, 바코드 매핑, 유통기한/Lot, 로케이션 바코드 라벨 출력

## 4. 두 시스템 간의 상호작용 및 데이터 동기화 메커니즘

```
[주문 확정 / 출하 오더]
        │
        ▼
[재고 할당 (Soft Allocation)] ──> [가용재고 차감, 총재고 유지]
        │
        ▼
[피킹 앱: 작업 진행]
        │
   ┌────┴───────────────────────────┐
   │                                │
[정상 피킹 완료]              [재고 부족 (CMD-SKIP)]
   │                                │
   ▼                                ▼
[실제 재고 영구 차감]         [재고관리 시스템으로 긴급 실사(Cycle Count) 오더 생성]
[출하 검수/포장 단계 인계]    [해당 로케이션 재고 이상 플래그 설정]
```

1. **소프트 할당(Soft Allocation)**: 
   * 주문이 인입되면 재고는 즉시 차감되지 않고 `allocated_qty`로 잠금(Lock) 처리되어, 다른 주문이나 일반 현장 불출로 인한 이중 출고를 방지합니다.
2. **피킹 예외와 재고 실사 자동 연계**:
   * 피커가 랙에서 재고 부족으로 `CMD-SKIP`을 스캔하면 피킹 작업은 중단 없이 다음 아이템으로 넘어가며, 재고 관리 시스템에는 즉시 **"해당 로케이션 실사 필요"** 이벤트가 트리거됩니다.
3. **자동 보충(Replenishment) 트리거**:
   * 피킹 완료 후 전면 피킹 랙의 수량이 안전 재고(Safety Stock) 이하로 떨어지면 재고 관리 시스템에 보충 작업 지시가 자동으로 생성됩니다.

## 6. 전체 WMS 환경에서 DB를 수정(Write/Update)하는 6가지 추가 프로세스

현재 연동 중인 `orderapp`(주문), `g-manager`(주문접수), `picking app`(피킹), `inventory app`(재고관리) 외에도, 창고 운영 전체 라이프사이클에서 DB를 수정하는 주요 주체와 프로세스는 다음과 같습니다.

```
[입고/적치] ──> [재고 보충/이동] ──> [주문/피킹] ──> [검수/포장/송장] ──> [출하/배송] ──> [반품/역물류]
    │                 │                 │                 │                │               │
 (DB 수정)         (DB 수정)         (기존 4개)        (DB 수정)        (DB 수정)       (DB 수정)
```

1. **검수 및 포장 (Inspection & Packing)**:
   * 피킹 완료 후 검수대에서 2차 바코드 검수 진행 시 상태를 `피킹완료` → `검수/포장완료`로 변경.
   * 몇 번 박스(Box ID)에 어떤 상품이 패킹되었는지 매핑 정보 기록(Insert/Update).
2. **송장 발행 및 배차 (Waybill & Dispatch)**:
   * 택배사 송장번호(Tracking No.) 또는 자체 배송 차량 정보를 주문 행에 입력.
   * 차량 상차 시 최종 **"출고 완료"** 확정 (재고 영구 차감).
3. **반품 및 역물류 (Returns & Reverse Logistics)**:
   * 반품 접수 시 반품 오더 생성(Insert).
   * 검수 결과 양품 판정 시 로케이션 재고 복구(+), 파손 판정 시 폐기 처리.
4. **재고 감모 및 손실 처리 (Loss & Scrap Adjustment)**:
   * 파손, 분실, 냉동 해동 사고, 유통기한 경과 상품 폐기 시 재고 차감 및 사유 코드 기록.
5. **배송 추적 및 완료 (Delivery Confirmation)**:
   * 택배사 배송 완료 웹훅 또는 배송기사 앱의 배송 완료 처리에 따른 최종 상태(`배송완료`) 업데이트.
6. **자동화 배치 및 스케줄러 (Scheduled Cron / Triggers)**:
   * 매일 자정 시점의 일마감 재고 스냅샷 기록(Insert).
   * 안전재고 미달 품목 자동 감지 및 발주/보충 알림 플래그 업데이트.
   * 결제/입금 대기 주문의 타임아웃 자동 취소 처리.

## 7. 다중 주체 동시 수정 환경의 DB 최적화 방안 (구글 시트의 한계 극복)

여러 앱과 작업자가 동시에 DB를 읽고 수정하는 환경에서 구글 시트를 직접 DB로 사용하면 치명적인 병목과 데이터 오류가 발생합니다. 이를 극복하기 위한 엔터프라이즈급 아키텍처 구성 방안입니다.

### 7.1 구글 시트의 치명적 한계 3가지
1. **행(Row) 단위 잠금(Lock) 및 트랜잭션(ACID) 부재**:
   * 피커 A가 바코드를 찍어 재고를 수정하는 순간(0.5초), 관리자가 주문을 승인하며 시트를 저장하면 앞선 피킹 수정분이 **덮어씌워져 유실(Lost Update)**됩니다.
2. **API 호출 제한(Rate Limit) 및 높은 레이턴시**:
   * Google Sheets API는 분당 300회(사용자당 60회) 제한이 있어, 피커들이 링 스캐너로 0.1~0.2초마다 스캔하면 순식간에 `429 Too Many Requests` 에러가 발생하고 앱이 정지됩니다.
3. **클라이언트의 직접 접근(Direct Access)에 따른 무결성 붕괴**:
   * 각 앱이 시트에 직접 접근하면 마이너스 재고 방지, 유효성 검증 로직이 앱마다 달라져 데이터 정합성이 깨집니다.

### 7.2 표준 3-Tier 아키텍처 구성 (중앙 API + RDBMS)
핵심 원칙: **"모든 클라이언트는 DB에 직접 접근하지 않고, 오직 중앙 백엔드 API를 통해서만 통신한다."**

```
[OrderApp]     [G-Manager]     [Picking App]     [Inventory App]
    │               │                │                  │
    └───────────────┼────────────────┼──────────────────┘
                    ▼ (초고속 HTTP / WebSocket)
        ┌─────────────────────────────────────────┐
        │       중앙 백엔드 API (Next.js / Node)    │
        │  • 비즈니스 검증 (마이너스 재고 차단)    │
        │  • 동시성 제어 (순차 큐 / 락 제어)        │
        │  • 트랜잭션 (전부 성공 or 전부 롤백)     │
        └────────────────────┬────────────────────┘
                             ▼
        ┌─────────────────────────────────────────┐
        │       관계형 데이터베이스 (RDBMS)        │
        │       (PostgreSQL 권장 / MySQL)          │
        │  • 행 단위 잠금 (Row-Level Locking)     │
        │  • 완벽한 ACID 트랜잭션 보장            │
        └────────────────────┬────────────────────┘
                             │ (선택: 비동기 읽기 전용 동기화)
                             ▼
        ┌─────────────────────────────────────────┐
        │      Google Sheets (조회 및 엑셀 보고서용) │
        └─────────────────────────────────────────┘
```

### 7.3 구글 시트 한계 극복을 위한 4대 핵심 기술
1. **RDBMS 원자적 차감 (Atomic Update)**:
   * 락 없이도 DB 엔진 레벨에서 마이너스 재고를 원천 차단:
     `UPDATE inventory SET qty = qty - 1 WHERE sku = 'ITEM-A' AND location_id = 'A-01-05-2' AND qty >= 1;`
2. **동시성 제어 (Pessimistic / Optimistic Locking)**:
   * **비관적 락(`SELECT FOR UPDATE`)**: 피커가 스캔한 로케이션의 재고 행을 0.05초간 잠궈 동시 출고 차단.
   * **낙관적 락(`Version` 컬럼)**: 주문 수정 등 충돌 빈도가 낮은 화면에서 충돌 감지 및 안내.
3. **인메모리 큐 / 버퍼링 (Queue / Redis)**:
   * 현장의 초고속 연속 바코드 입력을 백엔드 큐에 임시 적재 후 1ms 단위로 직렬화하여 DB에 반영.
4. **구글 시트의 역할 재정의 ("운영 DB" → "보고용 뷰어")**:
   * 트랜잭션은 PostgreSQL이 전담하고, 관리자용 일일 출고 집계나 재고 현황 리포트만 10분/1시간 단위로 백엔드가 구글 시트에 비동기 내보내기(Export/Sync) 수행.

### 7.4 추천 대안 및 현실적 마이그레이션 방안
* **대안 A. [강력 추천] Supabase (PostgreSQL 기반 BaaS)**:
  * 백엔드는 강력한 PostgreSQL 엔진으로 동작하지만, 관리자 콘솔이 **웹 스프레드시트(구글 시트/엑셀) UI**를 기본 제공하여 비개발자 관리자도 손쉽게 테이블 조회 및 수정 가능.
  * 실시간 웹소켓(Realtime) 지원으로 피킹 상태가 `g-manager` 화면에 즉시 무지연 반영.
* **대안 B. Next.js 백엔드 프록시 + Prisma + 비동기 시트 싱크**:
  * 모든 앱은 Next.js API(`api/wms/...`)만 호출하게 격리.
  * 백엔드에서 RDBMS(SQLite/PostgreSQL)에 우선 기록 후 백그라운드 워커가 구글 시트에 안전하게 반영.

## 8. 결론 및 단계적 실행 로드맵

1. **1단계 (기반 격리)**: 각 앱(`orderapp`, `g-manager`, `picking`, `inventory`)의 직접 DB 접근을 차단하고 Next.js 중앙 API 엔드포인트를 단일 창구로 지정.
2. **2단계 (메인 RDBMS 도입 및 스키마 설계)**: PostgreSQL(또는 Supabase)로 메인 DB를 승격하고, 구글 시트는 읽기/리포트용 뷰어로 분리.
3. **3단계 (피킹 PWA 우선 개발)**: 핵심 병목인 피킹 공정 속도 및 No-Click 워크플로우를 `/run` 라우트에 구현 (0.05초 이내 즉각 응답 보장).
4. **4단계 (재고 보충/실사 및 출하 검수 연동)**: 피킹 결품(`CMD-SKIP`) 처리, 입고 적치 및 송장/패킹 프로세스 완성.
5. **5단계 (관리자 관제 및 실시간 대시보드 구축)**: 웹소켓 기반의 실시간 피킹 진척률 모니터링 및 자동 배치 스케줄러 가동.
